THE CONVERGENCE (the module's spine — five points all three tools land on)
=========================================================================
1. A connection is a FILE, and it is usually checked into the repo. Claude Code
   .mcp.json / VS Code .vscode/mcp.json / Cursor .cursor/mcp.json. Sharing is the
   documented intent ("Include this file in source control to share MCP server
   configurations with your team" — VS Code).
2. A checked-in server is a PROPOSAL, NOT AN APPROVAL. Every tool gates it behind
   a trust step; Claude Code literally shows `⏸ Pending approval`.
3. NOBODY IS VETTING THESE FOR YOU. All three vendors say so in their own docs
   (Anthropic: "does not security-audit or manage any MCP server").
4. There is an ORG layer that decides which servers may run AT ALL — managed file /
   registry-only policy / dashboard allowlist. This is where the control actually is.
5. MATCH ON WHAT THE SERVER IS, NOT WHAT IT IS CALLED. A name is a user-assigned
   label. Claude Code states it outright: a serverName entry "is not a security
   control." This is L-3.1's "the list is not a boundary" one level deeper.

ORG CONTROL (managed-mcp.md) — the leader's menu, seven documented patterns:
  | Disable MCP        | managed-mcp.json with an empty server map              |
  | Fixed deployment   | managed-mcp.json with the servers you want             |
  | Approved catalog   | allowedMcpServers + allowManagedMcpServersOnly: true   |
  | Plugin servers only| strictPluginOnlyCustomization with `mcp` in the list   |
  | Soft allowlist     | allowedMcpServers WITHOUT allowManagedMcpServersOnly   |
  | Denylist only      | deniedMcpServers                                       |
  | No restrictions    | deploy nothing                                         |
  - managed-mcp.json paths: /Library/Application Support/ClaudeCode/ (macOS),
    /etc/claude-code/ (Linux+WSL), C:\Program Files\ClaudeCode\ (Windows). Delivered by
    MDM/GPO/Intune/Jamf — "cannot be set through server-managed settings."
  - If deployed: "Claude Code loads only the servers that file defines. Users cannot add,
    modify, or use any other MCP servers, including plugin-provided servers."
  - EVALUATION ORDER (verbatim headings): 1. Merge the lists. 2. Check the denylist —
    "A server that matches any denylist entry, by URL, command, or name, is blocked.
    Nothing overrides a denylist match." 3. Check the allowlist.
    => same deny-beats-allow law as L-3.1, now at the CONNECTION level.
  - allowManagedMcpServersOnly: true => "allowlists from user, project, and local
    settings are ignored. The denylist still merges from all sources, so users can
    always block servers for themselves." (Without it, a user can BROADEN your allowlist.)
  - MATCH KEYS: serverUrl (wildcards, hostname case-insensitive) / serverCommand (exact,
    every argument in order) / serverName.
    *** WARNING VERBATIM (load-bearing): "A `serverName` entry, in either list, is not a
    security control. The name is the label a user assigns when running `claude mcp add`
    or editing a config file, not the underlying server, so a user can call any server
    `github`. To enforce which servers actually run, add `serverCommand` or `serverUrl`
    entries." ***
  - allowedMcpServers UNSET = all allowed; EMPTY ARRAY [] = none allowed. (Not the same.)
  - Credentials: "Any user on the machine can read this file, so don't store API keys or
    other credentials in `env` blocks."
  - ROLLOUT UX CAVEAT (verbatim): a previously configured server newly blocked by policy —
    "The server silently disappears from /mcp and claude mcp list with no warning."
    => tell users before you enforce; a silent disappearance reads as a bug.
  - MONITORING: OpenTelemetry export with OTEL_LOG_TOOL_DETAILS=1 records which MCP
    servers and tools users invoke => the register can be checked against reality.
  - [M-10.3, 2026-07-25] namespacing "MCP tools are exposed to Claude as
    mcp__<server>__<tool>"; permission patterns mcp__<server> / mcp__<server>__<tool> /
    mcp__<server>__*; deny ["mcp__*"] blocks all MCP tools. Enterprise allowManagedMcpServersOnly.
  - [M-10.3 LIVE, the good failure — reused as labB] un-allowlisted tool under
    --permission-mode dontAsk = BLOCKED, and the agent REFUSED TO GUESS: "a payer/CPT
    coverage determination is exactly the kind of thing that shouldn't come from my

THE EXFILTRATION CONDITION  [SECONDARY — attributed, NOT vendor-sourced]
=========================================================================
"The lethal trifecta" — coined by Simon Willison, 2025-06-16
  (simonwillison.net/2025/Jun/16/the-lethal-trifecta/): an agent is exposed when it
  combines "Access to private data, exposure to untrusted content, and the ability to
  communicate externally." Hold any two and there is no exfiltration path; grant all
  three in one session and poisoned content can read private data and ship it out.
ATTRIBUTION DISCIPLINE: name Willison, do NOT imply a vendor coined or endorsed it.
VENDOR-VERIFIED SUPPORT for the mechanism (use these when stating it as fact):
  - Claude Code mcp.md: "Servers that fetch external content can expose you to prompt
    injection risk."
  - Claude Code security.md: "Isolated context windows: Web fetch uses a separate context
    window to avoid injecting potentially malicious prompts"; "Avoid piping untrusted
    content directly to Claude"; network-fetch commands (curl/wget) "are not auto-approved
    by default."
  - Cursor: MCP servers "can access external services and execute code on your behalf."
  - Cursor network modes (Allow all / Allowlist / Deny all) = the egress leg as a dial.

=========================================================================
MODULE FRAMING
=========================================================================
Analogy: the hospital's interface review / data-use agreement. No vendor gets a feed off
  the clinical data bus because an engineer liked it. Every interface gets reviewed:
  which fields, which direction, read or write, minimum necessary, who is the data
  steward, who signs. An MCP server is a new interface into your data — same review,
  same register, same signature. And you identify the interface by the system it actually
  is, not by the label someone typed in the config.
Spine: L-3.1 set how much the agent may DO; L-3.2 sets what it may REACH. The unit of
  governance is the CONNECTION, and approving one is a data-access decision.
Four moves: (1) treat it as a data-access review — direction, data class, blast radius;
  (2) put the decision in an ENFORCED org layer (managed set / registry-only / dashboard),
  not a repo file, because a checked-in server is a proposal; (3) match on identity
  (URL/command), never on name — the vendor says the name is not a security control;
  (4) know what the allowlist does NOT solve — an approved connector that ingests
  untrusted content plus an egress path is an exfiltration route (break one leg), and
  Copilot's content exclusion does not cover Agent mode.
The good failure (M-10.3, live): denied the data, the agent refused to invent a coverage
  determination. Design for refusal, not fabrication.
Deliverable: a connection register — every server with direction, data class, owner and
  approver of record — checked against real usage (OTEL), reviewed on a cadence.
Scope held: retention / training / IP / provenance / audit trail = L-3.4. Review policy
  for AI-written code = L-3.3. No new external claims needed by either from this sheet.
