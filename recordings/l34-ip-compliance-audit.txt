*** STANDING GUARDRAIL FOR THIS MODULE ***
This module is NOT legal advice and must never read as it. It teaches which questions a
leader must be able to answer, where the answers live, and what to get in writing. It does
NOT assert any vendor's compliance status, does NOT resolve who owns AI-generated output
(unsettled and jurisdiction-dependent), and does NOT summarize indemnity terms — those are
contract questions for counsel and procurement. Where a vendor states something in its own
docs, quote it and date it. Where they don't, say so.

=========================================================================
THE CONVERGENCE (the module's spine — three findings, all verified)
=========================================================================
1. YOUR DATA POSTURE IS PER-LOGIN, NOT PER-TOOL. The same binary on the same laptop against
   the same repo lands under a different data policy depending on which ACCOUNT the engineer
   signed into. All three vendors ship an enforcement mechanism for exactly this, which is
   the tell that it is a real and common failure.
2. THE VENDOR AUDIT LOG RECORDS ACCESS ADMINISTRATION, NOT DECISIONS. GitHub's Copilot audit
   log states it plainly: it "does not include client session data, such as the prompts a
   user sends to Copilot locally." What an auditor wants — who authorized this change, on
   what evidence — is not in any vendor's log. You build that from artifacts.
3. PROVENANCE CONTROLS ARE FILTERS, NOT A CHAIN OF CUSTODY. The duplication filter suppresses
   matches above a length threshold; it does not record where a suggestion came from, and
   GitHub's own responsible-use card puts the risk on the user.
=> Fourth honest caveat in a row for L-03 (after the native-Windows sandbox, content
   exclusion missing Agent mode, and AI review being advisory-not-gate): the artifact a
   leader assumes is "the audit trail" is an access log.

=========================================================================

(BUG-API-01 / M-12.3's UoW-3). Chosen because it is not a refactor: it changes WHO GETS
AUTO-APPROVED versus queued for human review, at exactly 0.85. That is a medical-necessity
policy change wearing a one-character diff — the perfect audit subject for a regulated shop.

  Q3 On what evidence?             ⚠ CONFIGURED the defense in the PR body (M-12.4) + M-12.3's
                                                boundary test pinning 0.85 -> AUTO_APPROVED,
                                                constant-referenced so it cannot drift.
  Q4 Which gates ran?              ⚠ CONFIGURED the CI/hook result on the commit. M-10.2's
                                                pre-commit gate DENYING a red commit is itself
                                                a record that the control fired.
  Q5 What was the agent told?      ✗ NOT CAPTURED  no vendor audit log holds the session
                                                ("does not include client session data").
                                                Partial recovery: the INSTRUCTION FILE is
                                                versioned in git (L-1.3), so you can show what
                                                rules were in force on that date.
  Q6 Where did the data go?        ⚠ CONFIGURED  depends which ACCOUNT was signed in. Enforce

                                                Cursor's Allowed Team IDs, managed seats.

  THE PAYOFF ROW — M-12.3's REFUSAL as the authority record: asked to make claim history a
  decision input, the agent STOPPED and refused: "that crosses the line from a code change

  not a passing test suite," naming a clinical lead, compliance/legal (payer contracts,
  CMS/state rules, disparate-impact risk for patients with prior denials, appealable reasons),
  and a shadow dry-run. That refusal is EXACTLY what an auditor wants to find — and it exists
  only because a human was the approver. "Human as approver, not typist" is an audit property.

=========================================================================
MODULE FRAMING
=========================================================================
Analogy: the medical record. If it isn't documented, it didn't happen. A chart audit does not
  ask whether the clinician remembers deciding; it asks the record to show who decided, when,
  on what evidence, under whose authority — exactly how you would reconstruct a prior-auth
  denial. Agent-written code lands in the same place, and the auditor's question is never
  "did the AI write it," it is "who authorized this change to the eligibility rule."
Spine: after the fact you must prove provenance, data flow and authority — and almost none of
  it is captured by default, so the audit trail is a design decision made BEFORE you need it.
Four moves: (1) reframe off "was AI involved" onto the three real questions; (2) know that
  provenance controls are filters, not custody; (3) fix the per-login data posture with an
  enforced login policy, and get training/retention/BAA answers IN WRITING from procurement,
  not from a docs page; (4) build the decision record out of artifacts you already produce —
  signed rule, gate result, PR + defense, and a refusal that names the sign-off — with depth
  following blast radius (L-1.2), not paperwork instinct.
Closes L-03 (permission -> data -> review -> proof) and hands to L-04 (economics).
