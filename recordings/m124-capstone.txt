DEFEND THE DIFF (the honest notes the agent surfaced for the reviewer to rule on)
  - WEB: "the badge fetches once on mount and never refreshes, so the count goes stale as
    reviewers work the queue" — named the follow-up (poll it on usePriorAuthStatus's interval).
  - WEB: npm install reported "2 high-severity vulnerabilities" — flagged, not touched (out of scope).
  - API: unknown-id/wrong-status behaviour inherited from the service; plants left alone by design.
  These are exactly what "defend the diff" means: the agent proposes and surfaces its own edges;
  the human reads the diff and decides. You are the approver, not the spectator.

THREE TIMES, ONCE PER TOOL (the capstone's comparison)

  tool-agnostic — the ceremony is identical in Copilot (delegate to the cloud agent -> PR) and
  Cursor; the student ships the same feature three ways and compares cycle time / diff / defend-
  ability (the labs). We did NOT re-run it in Copilot/Cursor here (that's the student's exercise
  and Copilot's cloud agent needs remote infra) — stated honestly, not claimed.

WHY THIS IS THE CAPSTONE
  Everything composes: an intent became units (M-12.2), the crew built the safe ones and stopped
  at the human decision (M-12.3), and here a full feature goes API -> UI -> tests -> PR with the
  quality metrics holding and the diff defended. The human's job across all of it was the two
  ends and the gates: state the intent, wire the guardrails, read the diffs, sign off. That is
  the whole course, executed once, end to end.
